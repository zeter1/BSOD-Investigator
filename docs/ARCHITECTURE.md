# Архитектура BSOD Investigator

Этот документ описывает логическую архитектуру проекта и помогает ориентироваться в основном исходном файле без необходимости читать его последовательно сверху вниз.

## Общая схема

```text
Windows crash artifacts
  ├─ Minidump / MEMORY.DMP
  ├─ Windows Event Log
  ├─ driver metadata
  └─ pre-crash telemetry
          ↓
     acquisition layer
          ↓
     CDB / WinDbg analysis
          ↓
   structured crash model
          ↓
 evidence extraction + normalization
          ↓
 driver candidate scoring
          ↓
 history correlation / deduplication
          ↓
 confidence + telemetry quality
          ↓
 UI / reports / support package / SQLite
```

Проект не должен делать вывод о причине BSOD только по одному имени файла из `!analyze -v`. Результат строится из нескольких источников доказательств и сопровождается оценкой уверенности.

## 1. Configuration and runtime paths

В начале приложения определяются:

- версия приложения;
- системные каталоги Windows;
- `Minidump` / `MEMORY.DMP` paths;
- LocalAppData-хранилище;
- каталоги reports / snapshots / logs;
- SQLite database;
- пользовательская конфигурация;
- видимая папка `Логи проблем` с fallback в LocalAppData.

Runtime-данные отделены от исходного кода и не должны попадать в репозиторий.

## 2. Domain models

Основные данные переводятся из необработанного текста и системных ответов в явные модели.

К ним относятся, в частности:

- конфигурация приложения;
- сведения о драйвере;
- кандидат-подозреваемый;
- результат анализа сбоя;
- диагностический контекст и исторические данные.

Такой слой нужен, чтобы scoring, UI и persistence работали со структурированными значениями, а не напрямую с сырым выводом CDB.

## 3. Dump discovery and acquisition

Приложение работает с:

- `%WINDIR%\Minidump`;
- `%WINDIR%\MEMORY.DMP`;
- дампом, выбранным пользователем вручную.

Перед анализом учитываются права доступа, существование файла и возможность чтения защищённых системных артефактов.

## 4. CDB / WinDbg execution

Внешний debugger рассматривается как отдельный управляемый процесс.

Ключевые требования:

- контролируемый запуск;
- потоковое чтение вывода;
- timeout;
- heartbeat / stage tracking;
- пользовательская отмена;
- корректное завершение с fallback от мягкой остановки к принудительной;
- отдельная диагностика проблем символов.

Процесс CDB не считается надёжным только потому, что он запустился: результат дополнительно разбирается и проверяется.

## 5. Crash evidence extraction

Из debugger output извлекаются признаки вроде:

- BugCheck;
- `IMAGE_NAME`;
- `MODULE_NAME`;
- `Probably caused by`;
- symbol / exception context;
- failure bucket;
- stack modules;
- process context.

Разные признаки имеют разную диагностическую силу и не должны трактоваться одинаково.

## 6. Driver metadata

Для кандидатов собираются дополнительные сведения:

- путь и имя файла;
- CompanyName / provider;
- версия;
- подпись и signer;
- product / description;
- INF/package metadata;
- состояние и режим запуска, где это доступно.

Важно различать:

- **Microsoft driver**;
- **third-party driver, подписанный Microsoft/WHQL**.

Microsoft signer сам по себе не превращает сторонний драйвер в системный драйвер Microsoft.

## 7. Evidence-based scoring

Scoring использует явные веса для разных типов признаков.

Сильные признаки получают существенно больший вес, чем общая метаинформация о драйвере. Metadata используется как корректирующий контекст, а не как замена crash evidence.

Пример логики:

```text
strong debugger evidence
        +
corroborating context
        +
historical independent crashes
        +
driver metadata adjustment
        ↓
     candidate score
        ↓
 confidence / level
```

## 8. Repeat-crash correlation

Повторяемость полезна только тогда, когда это действительно независимые падения.

Поэтому используется crash fingerprint и историческая корреляция, чтобы:

- повторный анализ одного dump не считался новым доказательством;
- несколько дампов одного и того же сбоя не завышали уверенность;
- repeat bonus основывался на независимых crash events с достаточным evidence.

## 9. Telemetry quality vs culprit confidence

Проект разделяет два разных вопроса:

1. **Насколько сильны доказательства против конкретного драйвера?**
2. **Насколько вообще качественные данные удалось собрать по этому сбою?**

Высокая уверенность в кандидате и высокая полнота телеметрии — не одно и то же.

Это уменьшает риск ложной точности, когда приложение показывает уверенный ответ при слабом наборе исходных данных.

## 10. Event Log correlation

События Windows около времени фактического падения используются как дополнительный контекст.

Они не должны автоматически становиться причиной BSOD, но могут:

- подтверждать временную связь;
- объяснять состояние устройства/драйвера;
- дополнять debugger evidence;
- помогать понять последовательность событий перед падением.

## 11. Pre-crash telemetry

Приложение может сохранять периодические snapshots системного состояния.

Их задача — предоставить контекст, которого уже невозможно получить после перезагрузки. Snapshots рассматриваются как вспомогательная телеметрия и не должны искусственно усиливать слабый crash evidence.

## 12. Persistence

SQLite используется для истории анализов и корреляции повторяющихся проблем.

Persistent layer должен обеспечивать:

- сохранение результатов;
- чтение истории;
- совместимость со старыми записями;
- исправление/миграцию устаревших данных без удаления полезной истории;
- защиту от дублирования одного crash event.

## 13. Reports and support packages

Для последующего анализа формируются структурированные отчёты и диагностические пакеты.

Их назначение:

- сохранить контекст ошибки;
- сделать проблему воспроизводимой;
- отделить важные данные от огромного сырого лога;
- упростить ручной анализ и анализ с помощью ChatGPT/Codex.

Crash dump может содержать чувствительную память, поэтому его включение в support package требует осознанного отношения к конфиденциальности.

## 14. Concurrency and lifecycle

Анализ dump — тяжёлая операция. Проект защищается от конфликтов через общий analysis lock.

Lifecycle операции должен иметь явные состояния:

```text
idle
  ↓
preparing
  ↓
running CDB
  ↓
parsing / enrichment
  ↓
scoring / persistence
  ↓
reporting
  ↓
finished | failed | cancelled
```

Это упрощает UI, отмену, логирование и восстановление понятного состояния после ошибки.

## 15. Self-test and CI

Встроенный `--self-test` проверяет критичную логику без необходимости реально вызывать новый BSOD.

В тестовый контур входят такие области, как:

- parsing debugger output;
- scoring;
- driver metadata classification;
- fingerprint / duplicate crash logic;
- history repair;
- telemetry quality;
- кодировки и другие регрессионные случаи.

GitHub Actions дополняет self-test синтаксической проверкой.

## Технический долг и направление развития

Текущая реализация исторически остаётся в крупном основном Python-файле. Логические границы уже существуют на уровне моделей и подсистем, поэтому при дальнейшем росте наиболее естественный рефакторинг — перенос этих границ в отдельные модули без изменения диагностических контрактов.

При таком рефакторинге важно сначала сохранить тестовый контур вокруг parsing, scoring, fingerprint/history и report generation, а уже затем физически перемещать код.

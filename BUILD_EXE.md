# Сборка BSOD Investigator в готовый EXE

`build_exe.bat` рассчитан на обычный Windows 10/11 и максимально автоматизирует подготовку рабочей сборки. Перед сборкой не требуется вручную устанавливать PyInstaller, создавать виртуальное окружение или отдельно искать Microsoft CDB.

## Самый простой способ

1. Скачайте репозиторий и распакуйте его в обычную папку с правом записи.
2. Дважды щёлкните `build_exe.bat`.
3. Если на компьютере отсутствуют **Debugging Tools for Windows**, BAT сам скачает официальный установщик Windows SDK с серверов Microsoft и попросит Windows установить только компонент отладчиков. В этот момент Windows может показать стандартный запрос UAC — это системное требование для установки CDB.
4. Дождитесь строки:

```text
[OK] READY BUILD CREATED AND VERIFIED.
```

5. Готовая программа находится здесь:

```text
dist\BSOD-Investigator.exe
```

После успешной обычной сборки дополнительных действий для запуска и анализа dump делать не нужно: Python-код находится внутри EXE, а необходимый системный `cdb.exe` уже должен быть установлен BAT-файлом.

## Что именно делает build_exe.bat

Скрипт выполняет полный pipeline:

1. Ищет **Python 3.13**, на котором проверяется упаковка проекта.
2. Если Python 3.13 отсутствует, пытается установить его для текущего пользователя через `winget`.
3. Создаёт `.build-venv`, изолированный от обычного Python пользователя.
4. Устанавливает в него `PyInstaller 6.22.3` и совместимые PyInstaller hooks.
5. Проверяет наличие Microsoft `cdb.exe`.
6. Если CDB отсутствует, загружает официальный `winsdksetup.exe` Microsoft и устанавливает только **Windows Desktop Debuggers / Debugging Tools for Windows**.
7. Компилирует Python-код.
8. Запускает безопасный встроенный self-test до упаковки.
9. Удаляет старые `build/`, `dist/` и `.spec`, чтобы старая сборка никогда не была выдана за новую.
10. Создаёт один оконный `dist\BSOD-Investigator.exe`.
11. Запускает `--self-test` уже на собранном EXE.
12. Сообщает об успешной сборке только если все предыдущие этапы завершились без ошибки.

## Почему есть build_support/sqlite_context_close.py

Python `sqlite3.Connection` при использовании через `with` выполняет commit/rollback, но стандартный context manager сам по себе не закрывает connection. На Windows это проявилось реальной блокировкой временного `history.sqlite3` во время packaged validation.

Проект использует короткоживущие SQLite-соединения в `with`-блоках, поэтому packaging runtime hook явно закрывает такое соединение при выходе из блока. Это устраняет Windows file lock и позволяет проверять упакованный EXE без подавления ошибки или отключения тестов.

## Microsoft Debugging Tools / CDB

BSOD Investigator анализирует crash dump через официальный `cdb.exe` из Microsoft **Debugging Tools for Windows**. Эти бинарники не копируются внутрь репозитория и EXE: вместо неясного перераспространения чужих системных компонентов обычный `build_exe.bat` устанавливает официальный компонент Microsoft на компьютер.

BAT использует официальный Windows SDK installer Microsoft и выбирает только feature:

```text
OptionId.WindowsDesktopDebuggers
```

Ожидаемый основной путь после установки:

```text
C:\Program Files (x86)\Windows Kits\10\Debuggers\x64\cdb.exe
```

Если CDB уже установлен, этот этап ничего не переустанавливает.

## Почему Windows может показать UAC

Установка системного компонента Microsoft в `Program Files (x86)\Windows Kits` требует административного подтверждения. BAT самостоятельно запускает официальный SDK installer с повышением прав; вручную открывать сайт, выбирать компоненты или вводить команды не нужно. Нужно только разрешить стандартный запрос безопасности Windows, если он появится.

## Повторная сборка

Повторно запустите:

```bat
build_exe.bat
```

Старый `dist/` будет очищен. `.build-venv` сохраняется для ускорения следующих сборок и автоматически пересоздаётся, если в нём оказалась неподходящая версия Python.

## CI / Codex

Для автоматической проверки:

```bat
build_exe.bat --ci
```

В `--ci` режиме:

- нет `pause`;
- возвращается корректный exit code;
- выполняются compile, self-test, PyInstaller build и packaged self-test;
- **не устанавливаются machine-wide Debugging Tools**, чтобы GitHub runner не тратил время и не изменял системное окружение ради packaging-smoke.

Обычная пользовательская сборка без `--ci` CDB устанавливает.

## Что считается успешной сборкой

Недостаточно того, что PyInstaller создал файл. Успех выводится только после запуска self-test самого файла:

```text
dist\BSOD-Investigator.exe --self-test
```

GitHub Actions отдельно проверяет этот Windows packaging pipeline.

## Если сборка завершилась ошибкой

BAT специально прекращает работу на первом критичном этапе и не пишет, что сборка готова. Смотрите первое сообщение `[ERROR]` выше итоговой строки.

Типовые причины:

- `winget` отсутствует и Python 3.13 ещё не установлен;
- сеть, proxy или антивирус блокирует `pip` либо загрузку Windows SDK с доменов Microsoft;
- пользователь отменил UAC при автоматической установке Debugging Tools;
- папка проекта защищена от записи;
- защитное ПО временно блокирует новый unsigned EXE.

## Что можно удалить после сборки

Безопасно удалить:

```text
build\
.build-venv\
BSOD-Investigator.spec
```

При следующей сборке нужные временные компоненты будут созданы заново.

Сам готовый EXE находится только в `dist\BSOD-Investigator.exe`. Установленный Microsoft CDB является системным диагностическим компонентом и остаётся в Windows Kits.
